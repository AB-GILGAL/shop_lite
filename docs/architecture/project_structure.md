# Project Structure

## Overview

The Shop Lite project follows a **Feature-First** folder organization combined with a **Clean Architecture** approach.

The project is organized to maximize:

- Scalability
- Maintainability
- Reusability
- Testability
- Readability

Each top-level folder has a single, well-defined responsibility.

---

# Root Directories

## android/

Contains the Android-specific project generated by Flutter.

Typical contents include:

- AndroidManifest.xml
- Gradle configuration
- Signing configuration
- Native Android code

Application business logic should never be placed here.

---

## ios/

Contains the iOS-specific project.

Typical contents include:

- Info.plist
- AppDelegate
- Xcode project
- Native Swift / Objective-C files

Business logic belongs in `lib/`, not here.

---

## web/

Contains configuration for Flutter Web.

## windows/

# The lib Directory

The `lib` folder is divided into four major modules.

```text
lib/
│
├── app/
├── core/
├── features/
├── shared/
└── main.dart
```

---

# app/

Contains application-level configuration.

Responsibilities include:

- Theme
- Routing
- Localization
- Application configuration
- Global constants

Example:

```text
app/
│
├── router/
├── theme/
└── localization/
```

Feature-specific logic should never be placed here.

---

# core/

Contains reusable infrastructure used across the application.

Typical modules include:

```text
core/
│
├── cache/
├── database/
├── errors/
├── network/
├── services/
├── utils/
└── extensions/
```

The `core` module should remain independent of individual features.

---

# features/

Contains all business features.

Each feature owns its own implementation.

Example:

```text
features/
│
├── products/
├── categories/
├── search/
├── favorites/
└── settings/
```

Each feature follows the same internal structure.

```text
products/
│
├── data/
├── domain/
├── presentation/
└── providers/
```

This keeps features isolated and easier to maintain.

---

# shared/

Contains reusable UI components used by multiple features.

Example:

```text
shared/
│
├── widgets/
├── dialogs/
├── loaders/
├── animations/
└── extensions/
```

Shared components should never depend on a specific feature.

---

# main.dart

Application entry point.

Responsibilities include:

- Flutter initialization
- Dependency initialization
- App startup
- Error handling setup

Business logic should remain outside this file.

---

# Folder Naming Conventions

The project follows these naming rules.

Folders:

```text
snake_case
```

Examples:

```text
product_details

network_client

shared_widgets
```

Files:

```text
snake_case.dart
```

Examples:

```text
product_repository.dart

dio_client.dart

network_configuration.dart
```

Classes:

```text
PascalCase
```

Examples:

```text
ProductRepository

NetworkConfiguration

PrimaryButton
```

Variables:

```text
camelCase
```

Examples:

```text
productRepository

baseUrl

networkStatus
```

Constants:

```text
camelCase
```

Examples:

```dart
const appName = 'Shop Lite';
const defaultPadding = 16.0;
```

Static constant members should also use `camelCase`.

---

# Design Principles

The project structure follows these principles:

- One responsibility per folder.
- One responsibility per file.
- Feature isolation.
- Minimal coupling.
- Maximum reusability.
- Predictable folder organization.

---

# Future Expansion

As the application grows, additional feature folders will be added without affecting the existing structure.

Examples:

```text
features/
│
├── authentication/
├── cart/
├── checkout/
├── orders/
├── profile/
└── notifications/
```

The architecture is designed to scale without major restructuring.
